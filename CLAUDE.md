# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

CheckTur Piura — hackathon web app (Spanish UI). **The core is VERIFYING**: one search box auto-detects RUC, celular/WhatsApp/Yape/Plin, bank account, plate or name and returns a verdict about who it belongs to; QR codes on vans/staff cards/shopfronts open live verification pages; a secondary directory lists verified companies per destination (no prices, no reviews). Read `CHECKTUR_CONTEXTO.md` (legal domain + product rules), `BLUEPRINT.md`, `docs/DISENO.md` (design system "Sello"), `docs/VERIFICACION.md` (data model) and **`PENDIENTE.md` (routes, demo cases, what's next)** before working. `AGENTS.md` applies: this is Next.js 16 — check `node_modules/next/dist/docs/` before using Next APIs.

## Commands

```bash
npm run dev                       # local dev
npm run build                     # also type-checks; run `npx next typegen` if PageProps types are missing
npm run lint
npm test                          # node:test via tsx: lib/*.test.ts lib/**/*.test.ts
npx tsx --test lib/dictamen.test.ts   # single test file
npm run e2e                       # operator→admin→tourist flow against the REAL Supabase project; needs `npx next start -p 3456` running; creates and deletes its own data
npm run load:sunat -- <padron.txt> [AAAA-MM-DD]   # load SUNAT padrón reducido (needs SUPABASE_SERVICE_ROLE_KEY)
```

Deploy: Vercel project `checktur-piura`, auto-deploys on push to `main` (https://checktur-piura.vercel.app). Env vars (`.env.example`): Supabase URL + publishable key, `SUPABASE_SERVICE_ROLE_KEY` (server only; also the HMAC key source in `lib/firma.ts`), `GEMINI_API_KEY`.

## Architecture

- **Stack**: Next.js 16 App Router with `cacheComponents: true` → every page that reads `params`/`searchParams`/cookies/DB is a thin shell + an async component inside `<Suspense>`; call `await connection()` before `new Date()`. Middleware is `proxy.ts` (only refreshes Supabase session on `/operador`, `/admin`, `/ingresar`).
- **Supabase is the backend.** Schema lives only in `supabase/migrations/` (applied to the remote project via the Supabase MCP `apply_migration`; after applying, rename the local file to the version reported by `list_migrations`). `lib/database.types.ts` is generated — regenerate after migrations. Seed data (`supabase/seed.sql`) is fictitious: RUC `209999999xx`, plates `MUE###`, names with "(muestra)"; never invent data about real companies.
- **Security model (non-obvious, enforced in SQL):** Supabase grants ALL on new tables by default, so migrations `revoke all` then grant per column. Tourists (anon) only read registries and public review columns. `submissions` and `reviews` are **inserted only by server actions with the service-role client** after validation (no INSERT grant). `review_contactos` has no grants at all. Admin = `app_metadata.rol = 'admin'` (`es_admin()` in SQL, `exigirAdmin()` in `lib/sesion.ts`); pages that read with service role must call `exigirAdmin()` first.
- **Dictamen (verdict)**: `lib/dictamen.ts` pure rules → estado `verificado | observaciones | actualizacion | no_encontrado | alerta`. All tourist-facing text lives in `config/textos.ts` (wording rules: never "informal/ilegal/estafa/fraude"); tunable values in `config/reglas.ts`. Data access for the tourist flow in `lib/consultas.ts` (input → `clasificarEntrada` → `resolver`; name search is the SQL RPC `buscar_prestadores` using `normalizar_nombre`).
- **Image/AI seam**: `lib/vision/gemini.ts` is the only provider-specific file (REST + JSON Schema). `lib/vision/index.ts` defines schemas and sanitizes model output (treat it as untrusted). Used for: photo search (`lib/consulta-imagen.ts`, priority RUC > plate > social account/phone > name), operator documents, and review receipts.
- **Ad observations** (from a photo search) never go in the URL and never change the official estado: stored in a signed httpOnly cookie (`lib/anuncio.ts`) and shown in a separate block.
- **Operator flow**: browser uploads straight to Storage bucket `documentos/<user_id>/…` (avoids Vercel body limit) → `app/operador/acciones.ts` validates and inserts → `lib/validacion.ts` hashes, extracts and runs the 8 verification layers in `lib/checks/` (pure) → admin approves in `/admin` → `publicarValidacion` publishes the provider as "En proceso de actualización" for 60 days using only SUNAT/document data (never operator-declared name/phone).
- **Agency side** (`lib/agencia.ts`, `lib/agencia-validar.ts`, `/operador/agencia/[id]`): an account administers a provider only after an admin approves a document for that RUC (`publicarValidacion` → `proveedor_cuentas`, one owner per provider). Profile edits go to `proveedor_cambios` (pending) and are applied only when the admin approves (`/admin/cambio/[id]`) — the phone is what the catalog's WhatsApp button uses. New services enter `services` as `pendiente`; the admin publishes them (`/admin/servicio/[id]`). Channels, vehicles and staff added by a company enter `pendiente` and are approved in `/admin` (`resolverAlta`); a channel can't be approved for two companies (unique index). Server-only tables (`proveedor_cuentas`, `proveedor_cambios`, `review_contactos`, `limites`, `reportes`) have RLS on and no grants/policies by design (advisor INFO lints are expected). Always call `exigirDueno`/`exigirAdmin` before service-role reads.
- **Rate limit** (`lib/limite.ts`): photo search, operator documents and tourist reports → `hayCupo(accion)` counts per hashed IP/user in Postgres (`consumir_cupo`); limits in `config/reglas.ts`.
- **Reviews**: public UI removed in the refocus (tables `reviews`/`review_contactos` kept; `/admin/resena/[id]` still moderates existing ones).
- **Verification model** (`docs/VERIFICACION.md`): `canales` (whatsapp/telefono/yape/plin/banco/redes/web; `valor` = normalized search key, bank = sha256, never exposed — searched server-side in `lib/consultas.ts` `empresasPorCanal`), `personal` (DNI: last 3 digits only), `empresa_destinos` (fixed list `DESTINOS`), vehicle `foto_url`/`autorizacion_mtc`/`aprobacion`, `reportes`. Input detection: `clasificarEntrada` in `lib/normalizacion.ts` (shared with the client chip). Verdict: `dictamenPrestador(…, { vehiculos, personal })` — expired SOAT/CITV/carné ⇒ "observaciones" automatically (also over "actualizacion"). QR: `/v/[id]` resolves company/vehicle/person (`resolverQr`); printable sheet `/operador/agencia/[id]/qr` (`qrcode`, print-to-PDF); scanner `/escanear` (`BarcodeDetector` + `jsqr`). The old priced catalog (`/experiencia`, `/guardados`, opinions UI) was removed; `/explorar` redirects to `/destinos` (next.config). `services` remains only as service names.
- **Design system "Claro" v1** (`docs/DISENO.md`): brand blue `#056CF2` on cool whites; shadcn/ui (Radix, `components.json`) primitives in `components/ui/*.tsx`, **adapted** (44 px targets, 16 px text, solid focus, no `transition-all`, `cn` from `@/lib/utils`) — re-adapt any newly added shadcn component the same way. CheckTur components (`Sello`, `InsigniaEstado`, `ChipProceso`, `Campo`, `Tarjeta`, `Plegable`, `Encabezado`, `Aviso`, `BarraAccion`, `claseBoton`, …) live in `components/ui/index.tsx`; pages import everything from `@/components/ui`. Tokens only in `app/globals.css` (light + dark via `prefers-color-scheme`, no toggle; old names like `bg-superficie` are aliases). "En proceso de actualización" is **violet** (not blue: blue = brand/actions). `text-primary` fails AA as small text on the background — use `text-enlace` for blue text. Fonts Geist / Geist Mono (`<Mono>` only for RUC, plates, n.°, dates). Motion utilities in globals.css (`.pulsable`, `.elevable`, `.entrada`, `.escalonado`, `.chip-entrada`; reduced-motion keeps fades only). Showcase at `/estilos`. Components use semantic tokens, never raw colors (only exceptions: the license `Placa` and the scanner overlay). UI glossary: "proveedor"/"empresa" (never "prestador"/"operador" in visible text; routes/code names unchanged); no first-person voice.
- Demo/test fixtures: `data/muestras/` (see its `LEEME.md`).
